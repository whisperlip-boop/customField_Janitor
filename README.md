# Custom Field Janitor

Jira Server / Data Center 관리자용. **커스텀 필드 하나를 지워도 되는지** 판단할 재료를 모아 보여준다.
v1은 **조회 전용**이다 — 이 앱은 아무것도 지우지 않는다.

- 앱 이름: Custom Field Janitor
- 메뉴: 관리 > 이슈 > 필드 > **필드 사용처** (`/secure/admin/CustomFieldUsage.jspa`)
- plugin key: `com.bskim.jira.janitor`

## 문제

Jira를 몇 년 운영하면 커스텀 필드가 수백 개가 된다. 그런데 정리하려고 보면
Jira가 판단 재료를 주지 않는다.

| 알고 싶은 것 | 기본 관리 화면 |
|---|---|
| 이 필드에 값이 들어 있는 이슈가 몇 개인가 | **없음** |
| 어떤 워크플로가 참조하는가 | 없음 |
| 어떤 필터·가젯에서 쓰이는가 | 없음 |
| 권한·알림 스킴이 참조하는가 | 없음 (지우면 권한이 조용히 깨진다) |
| 걸린 화면이 결국 어느 프로젝트에 닿는가 | 화면 이름까지만 |

결과적으로 관리자는 필드를 지우지 못하고 계속 쌓는다.

## 해결 — 상태 라벨 하나로 답한다

세 축을 독립적으로 확인해 필드마다 라벨 하나를 붙인다.

| 라벨 | 조건 | 뜻 |
|---|---|---|
| **위험** | 앱이 잠근 필드(`LOCKED`)이거나, 워크플로(조건/검증기/함수) 또는 권한·알림·이슈보안 스킴이 참조 | 지우면 기능이 조용히 깨진다 |
| **고아 데이터** | 값 있는 이슈 > 0, 화면 참조 = 0 | 화면에서 빠졌는데 데이터는 남았다. 지우면 정보 손실 |
| **활성** | 값 있는 이슈 > 0, 화면 참조 > 0 | 정상 사용 중 |
| **방치** | 값 있는 이슈 = 0, 화면 참조 > 0 | 화면에만 걸려 있다. 권장 조치는 삭제가 아니라 "화면에서 제거" |
| **미사용** | 값 0, 사용 증거 참조 0 | 삭제 안전. 청소 1차 대상 |

각 라벨의 조건과 권장 조치, 그리고 왜 [고아 데이터]와 [방치]를 혼동하면 안 되는지는
앱 안의 사용 설명서에 있다 — 목록 화면의 "이 화면을 읽는 방법" 링크.

판정 우선순위는 위험 > 고아 데이터 > 활성 > 방치 > 미사용이다.
목록의 기본 정렬은 그 역순(청소 대상이 위)이다.

모든 처리는 **필드 ID 기준**이다. 같은 이름의 필드가 여러 개 있는 것이 정리 대상
인스턴스의 정상 상태이므로, UI에는 항상 ID를 함께 노출하고 이름 중복은 경고로 표시한다.

## 무엇을 훑는가

| 축 | 대상 | 방법 |
|---|---|---|
| A · 데이터 | 값 있는 이슈 수 / 값 행 수 | `customfieldvalue`, `label` 단일 GROUP BY (필드가 500개여도 쿼리 2번) |
| A · 보조 | 마지막 값 변경일 | `changeitem` + `changegroup` (이름 기반이라 중복 이름이면 "부정확" 표시) |
| B · 설정 | 화면, 화면→화면스킴→ITSS→프로젝트 체인 | `FieldScreenManager` + 프로젝트에서 역방향 |
| B · 설정 | 필드 설정(표시/숨김/**필수**) | `FieldLayoutManager` |
| B · 설정 | 컨텍스트(적용 범위) | `CustomField.getConfigurationSchemes()` |
| B · 동작 | 워크플로 조건/검증기/전·후처리 함수/전이 화면 | 디스크립터 재귀 순회 + arg 값 문자열 스캔 |
| C · 조회 | 필터(JQL) | `SearchRequest` 전체 + `JqlQueryParser` (이름 참조와 `cf[ID]` 참조 둘 다) |
| C · 조회 | 권한 / 알림 / 이슈 보안 스킴 | `SchemeManager.getSchemeObjects()` (`userCF`, `groupCF`, `*_Custom_Field_Value`) |
| C · 조회 | 대시보드 가젯 | `gadgetuserpreference` 문자열 스캔 |
| C · 조회 | 이슈 네비게이터 컬럼 | `columnlayout` + `columnlayoutitem` (시스템 기본 / 필터 / 개인 설정을 구분한다) |
| 소유 | 앱이 잠근 필드 (Sprint, Epic Link, Rank …) | `managedconfigurationitem` 단일 쿼리 (앱이 비활성이어도 잡힌다) |
| D · 심층 | 앱 테이블(`AO_*`)의 문자열 | 별도 버튼으로 실행. **참조가 아니라 문자열 일치**이므로 라벨에 반영하지 않고 따로 보여준다 |

각 항목에는 해당 Jira 관리 화면 링크가 붙는다. 실제 삭제·수정은 Jira 표준 화면에서 한다.

## 포함되지 않은 것 (UI에도 같은 문구로 표시된다)

- Agile 보드 설정(카드 레이아웃, 빠른 필터, 추정 필드, 스윔레인)
- 서드파티 앱이 자체 `AO_*` 테이블에 저장한 설정
- 값을 앱 자체 테이블에 저장하는 필드 타입(Rank 등) — 값이 0으로 나온다.
  단 그런 필드는 대개 앱이 잠근 필드라서 [위험]으로 잡히고 삭제 링크가 숨겨진다

**여기서 "참조 없음"은 삭제해도 안전하다는 증명이 아니다.** 도구가 자기 한계를 말하지
않으면 관리자가 잘못된 확신으로 필드를 지운다.

읽지 못한 항목은 조용히 빠지지 않고 화면 하단 **"확인 불가"** 목록에 나온다
(예: JQL 파싱이 안 되는 깨진 필터).

## 화면

1. **목록** — 상태 / 필드명+ID / 타입 / 값 있는 이슈 수 / 값 행 수 / 마지막 변경 /
   화면·워크플로·필터·가젯 수 / 참조 합계. 상태·이름·타입 필터와 컬럼 정렬, CSV 내보내기.
2. **상세** (`?fieldId=customfield_10001`) — 참조를 종류별 표로. 화면은 프로젝트 체인까지,
   워크플로는 전이 이름과 위치(조건/검증기/후처리 함수)까지. 하단에 판단 요약 한 줄.
3. **기존 커스텀 필드 관리 화면 주입** — `ViewCustomFields.jspa`의 각 행에 상태 배지,
   값 건수, "사용처" 링크를 덧붙인다. 스캔 결과가 없으면 아무것도 주입하지 않는다.
세 화면 모두 우측 상단에 **한국어/영어 토글**이 있다(`?lang=ko` / `?lang=en`).
파라미터가 없으면 보는 사람의 Jira 로케일을 따르고, 화면을 오갈 때 선택한 언어가 유지된다.
링크로 공유하면 받는 사람도 같은 언어로 본다.

4. **사용 설명서** (`/secure/admin/CustomFieldUsageHelp.jspa`) — 목록 화면 안내 문구 옆
   링크로 들어간다. 우측 상단에 한국어/영어 토글(`?lang=ko`), 우측에 스크롤을 따라오는
   색인. 컬럼·상태 라벨·배지·상세 화면 항목의 의미와 삭제 판단 기준(삭제 무방 / 확인 필요 /
   지금은 안 됨)을 담았다. 라벨과 참조 카테고리 표는 열거형을 순회해 만들므로 코드가
   바뀌면 설명서도 따라간다.

## 스캔

"지금 스캔" 버튼으로 시작하는 비동기 작업이다. 실시간 조회는 하지 않는다 —
관리자 도구는 예측 가능한 게 실시간보다 낫다.

- 단계별 진행률을 REST 폴링으로 노출한다(필드 → 값 → 화면 → 필드설정 → 컨텍스트 →
  워크플로 → 필터 → 스킴 → 가젯 → 네비게이터 컬럼)
- 진행 중 재요청은 409로 거부하고 현재 진행률을 준다
- 결과는 메모리에 두고 **Jira DB(플러그인 설정)에 스냅샷으로 남긴다.** 재기동·재배포
  뒤에도 마지막 표가 그대로 있다. 플러그인 버전이 바뀌면 스냅샷을 버리고 "아직 스캔한 적
  없음"으로 돌아간다(로그에 이유가 남는다) — 수집기가 늘어난 새 버전이 옛 스냅샷을 읽으면
  그 참조가 빠진 채 표가 그려지기 때문이다. 업그레이드 뒤에는 스캔을 한 번 다시 누른다
- Data Center 다중 노드에서는 스캔하지 않은 노드가 자기가 마지막으로 읽은 스냅샷을
  보여준다. 그래서 화면에 항상 스캔 시각을 함께 보여준다
- 대규모 인스턴스에서는 업무 시간 외 실행을 권하는 문구를 화면에 넣었다

## REST

`/rest/janitor/1.0/` — 전 엔드포인트가 **Jira 관리자**(`ADMINISTER` 전역 권한)를
서버측에서 다시 검사한다. 시스템 관리자가 아니라 Jira 관리자인 것은 의도다 —
Jira 기본 `ViewCustomFields.jspa` 와 같은 기준이라, 커스텀 필드를 관리할 수 있는
사람이면 그 사용처도 볼 수 있다.
권한 없으면 403이고 본문에 이유를 담지 않는다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/fields` | 캐시된 전체 결과 + 스캔 상태 + 확인 불가 목록 |
| GET | `/fields/{id}` | 필드 하나의 상세 (`10001` 또는 `customfield_10001`) |
| POST | `/scan` | 스캔 시작 (202) / 진행 중이면 409 |
| GET | `/scan/status` | 진행률 폴링 |
| GET | `/fields.csv` | CSV 내보내기 (Excel용 BOM 포함) |

```bash
curl -u "$JIRA_USER:$JIRA_PASS" -X POST -H 'X-Atlassian-Token: no-check' \
     "$JIRA_BASE/rest/janitor/1.0/scan"
curl -u "$JIRA_USER:$JIRA_PASS" "$JIRA_BASE/rest/janitor/1.0/fields" | jq '.fields[] | {name, status, issuesWithValue}'
```

## 빌드 / 설치

```bash
DOWNLOADS=/path/to/dir ./build.sh   # 빌드 후 jar를 그 폴더로 복사
./deploy.sh                         # 실행 중인 Jira(UPM)에 업로드
python3 tools/make-i18n.py          # i18n/*.src → src/main/resources/*.properties (한글 escape)
```

인스턴스 주소·계정은 저장소에 두지 않는다. 스크립트는 전부 환경변수로 받는다 —
`JIRA_BASE`, `JIRA_USER`, `JIRA_PASS`. `build.sh` 의 복사 위치는 `DOWNLOADS` 이고,
저장소 루트에 `.build.local`(추적 안 함)로 고정해 둘 수 있다.

대상: Jira 8.17.1 / 개발·테스트: docker Jira 8.13.0.
낮은 쪽(8.13)으로 컴파일한 jar가 8.17.1에 그대로 설치·동작한다(반대는 보장 안 됨).

그 가정은 실측으로 확인한다. 운영 타깃 버전에서 직접 돌려보는 프로필이 있다 —
컴파일은 8.13.0으로 유지되고 실행만 8.17.1이 된다. 라이선스 키는 필요 없다
(AMPS가 개발용 라이선스를 자동으로 넣는다):

```bash
sleep infinity | atlas-run -Pjira817                            # localhost:2990/jira, admin/admin
./tools/probe-jira.sh http://localhost:2990/jira admin admin      # 버전 의존 항목 수집
./tools/probe-jira.sh "$JIRA_BASE" "$JIRA_USER" "$JIRA_PASS"     # 8.13 기준값
```

`tools/probe-jira.sh`는 아무 인스턴스에서나 web-item section 키, 관리 화면 렌더링 방식,
행 후크 속성, 잠긴 필드 목록, 권한·웹수도 동작을 뽑아낸다. 두 버전에서 돌려 대조하며,
결과는 [docs/01-버전대조-8.13-vs-8.17.1.md](docs/01-버전대조-8.13-vs-8.17.1.md)에 있다.

## 테스트 픽스처

```bash
python3 tools/make-testdata.py          # 필드 A~I + 필터 + 가젯
./tools/make-workflow-fixture.sh        # 픽스처 E의 워크플로 참조
```

| 픽스처 | 의도 | 기대 |
|---|---|---|
| A | 화면 + 값 | 활성 |
| B | 화면만 | 방치 |
| C | 값 입력 후 화면에서 제거 | 고아 데이터 |
| D | 아무 곳에도 안 씀 | 미사용 |
| E | 워크플로 검증기·후처리 함수·중첩 조건 | 위험 (확정 3건 + 추정 1건) |
| F | 권한 스킴 `userCF` **세 권한**(Browse/Edit/Assign) + 알림 스킴 | 위험, 참조 4건 |
| G | A와 같은 이름 | 중복 경고, 별도 행 |
| H | 멀티 사용자 선택, 이슈 1건에 값 2개 | 이슈 1 / 행 2 |
| I | 라벨 타입 (`label` 테이블 저장) | 이슈 1 / 행 3 |

## 설계 결정과 실측

기획서와 다르게 판단한 부분은 전부 근거와 함께 [docs/00-환경실측.md](docs/00-환경실측.md)에 있다.
