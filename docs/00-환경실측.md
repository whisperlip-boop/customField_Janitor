## API 실측 (jira-api 8.13.0, javap)

기획서와 다르게 정한 것이 하나 있다.

- **JDBC 커넥션은 `com.atlassian.jira.database.DatabaseAccessor` 로 얻는다.**
  기획서 5.1은 `com.atlassian.jira.ofbiz.DefaultOfBizConnectionFactory` 를 지목했지만
  그 클래스는 jira-api에 없다(jira-core 내부). `DatabaseAccessor` 는 jira-api 8.13에
  공개되어 있고 필요한 것을 다 준다:
  ```
  <R> R executeQuery(ConnectionFunction<R>)   // DatabaseConnection#getJdbcConnection
  Optional<String> getSchemaName()            // 스키마 프리픽스
  DatabaseVendor getDatabaseVendor()          // 방언 판단
  ```
  기획서의 근거(schema-name 존중 / try-with-resources / 직접 SQL은 DAO 한 곳)는
  그대로 지켜진다. 오히려 공개 API라 상위 버전 호환이 낫다.

- 나머지는 기획서대로 전부 존재: `FieldScreenManager`, `FieldScreenSchemeManager`,
  `IssueTypeScreenSchemeManager`, `FieldLayoutManager`, `WorkflowManager`,
  `WorkflowSchemeManager`, `JqlQueryParser`, `OfBizDelegator`,
  `GlobalPermissionManager`, `SchemeManager#getSchemeObjects`.
- `JiraWebActionSupport` 도 jira-api에 있다 → webwork1 액션에 jira-core 의존이 필요 없다.

### 워크플로 순회에서 기획서가 놓친 지점 (함정 3 확장)

`ActionDescriptor.getPostFunctions()` 는 사실상 **pre-function 자리**다.
Jira UI가 "후처리 함수(post function)"라고 부르는 것은 여기 없다.

실제로 훑어야 하는 곳:
```
action.getValidators()
action.getPreFunctions() / action.getPostFunctions()
action.getUnconditionalResult().getValidators() / getPreFunctions() / getPostFunctions()   ← UI의 후처리 함수
action.getConditionalResults()[*] 의 위 3종
action.getRestriction().getConditionsDescriptor()  → 재귀 (중첩 ConditionsDescriptor)
step.getPreFunctions() / step.getPostFunctions()
```
`JiraWorkflow.getAllActions()` 가 ordinary/global/initial/common 전이를 다 준다.
스텝 단위 함수는 `getDescriptor().getSteps()` 로 따로 훑는다.

# 구현 중 실측으로 바뀐 것 (기획서와 다른 판단)

0장 원칙("실측이 문서를 이긴다")에 따라 바꾼 것들이다. 전부 근거를 붙였다.

## 1. web-item의 section 값 — 기획서 기대값도, JSP의 meta 값도 아니다

Jira 설치본 `WEB-INF/classes/webfragment/system-admin-sections.xml` 실측:

```xml
<web-section key="element_options_section" location="admin_issues_menu" weight="10"/>
<web-section key="fields_section"          location="element_options_section" weight="40"/>
<web-item    key="view_custom_fields"      section="element_options_section/fields_section" weight="10"/>
```

- 기획서 기대값 `admin_issues_menu/fields_section` → **메뉴가 안 나온다**
- JSP의 `admin.active.section` 값 `admin_issues_menu/element_options_section/fields_section`
  → 이것도 web-item의 section으로는 **안 나온다**
- 실제로 동작하는 값: **`element_options_section/fields_section`**

즉 `admin.active.section` 메타(사이드바 하이라이트용, 3단 경로)와 web-item의 `section`
(2단 경로)은 형식이 다르다. 둘을 혼동하면 조용히 메뉴가 사라진다 — 에러도 로그도 없다.

우리 화면 템플릿은 하이라이트용으로 3단 메타를 쓰고, web-item은 2단 section을 쓴다.

## 2. condition 클래스를 직접 만들었다

기획서 7.1은 `JiraGlobalPermissionCondition`을 쓰라고 했다. 실측 결과 3단계로 막혔다:

1. XML에만 등장하는 클래스라 bnd가 Import-Package에 안 넣는다 → `ClassNotFoundException`
2. Import-Package에 넣으면 → `Plugin has no container`
   (web fragment의 condition은 플러그인 Spring 컨테이너로 주입된다)
3. `<Spring-Context>*</Spring-Context>`로 컨테이너를 만들면 →
   `No qualifying bean of type GlobalPermissionManager`
4. `<component-import>`로 그 빈을 넣으려 하면 → AMPS `validate-manifest`가 빌드를 막는다
   ("atlassian-plugin.xml contains a definition of component-import.
     This is not allowed when Atlassian-Plugin-Key is set.")

그래서 인수 없는 생성자를 가진 `AdminOnlyCondition`을 직접 만들고 권한 판단은
`AdminGuard`(액션/REST와 동일한 판단)에 맡겼다. `<Spring-Context>*</Spring-Context>`와
빈 없는 `plugin-context.xml`은 컨테이너를 만들기 위해 그대로 둔다.

## 3. 필드 목록은 `CustomFieldManager`만으로는 부족하다

`CustomFieldManager.getCustomFieldObjects()`가 11개 중 **5개만** 돌려줬다.
빠진 6개는 Jira Software(greenhopper)가 제공하는 Epic Link / Epic Status / Epic Name /
Epic Color / Sprint / Rank — 타입 제공 앱이 살아 있지 않으면 목록에서 아예 빠진다.

정리 도구에서 이건 치명적이다. 앱을 지웠는데 필드와 값만 남은 상태가 정확히 청소
대상이고, 목록에 없으면 관리자는 그 필드가 없다고 믿는다.

→ 존재의 근거는 `customfield` 테이블로 바꾸고, 타입 이름 같은 표시 정보만
   `CustomFieldManager`에서 보충한다. API로 다룰 수 없는 필드는 목록에
   "타입 없음"으로 표시한다.

## 4. 숫자 ID 단독 매칭은 [위험] 라벨을 망친다

기획서 5.3(5)는 워크플로 arg에서 `customfield_<id>`와 **숫자 ID 단독** 둘 다 잡으라고
했다. 그대로 구현했더니 Jira 기본 워크플로에서 이게 걸렸다:

```xml
<arg name="field.name">resolution</arg>
<arg name="field.value">10000</arg>   <!-- 해결책 ID 10000 -->
```

커스텀 필드 ID와 해결책·상태·화면·스텝 ID가 같은 10000번대를 쓰기 때문에 구조적으로
충돌한다. 그대로 두면 `Development` 필드가 [위험]으로 찍혔다(워크플로 참조 3건).
3장은 "이 라벨이 앱의 정체성"이라고 했는데, 기본 필드가 전부 위험이면 라벨이 무의미하다.

→ 두 가지로 나눴다:
  - `customfield_<id>` 일치 = 확정 참조, 위험으로 센다
  - 숫자 ID 단독 일치 = 추정 참조("숫자 ID 일치(추정)"), 목록에는 나오지만 위험으로 안 센다
  - Jira 기본 제공 구현(`class.name`이 `com.atlassian.jira.`로 시작)에서는 숫자 단독
    탐색을 끈다. 기본 구현은 커스텀 필드를 항상 `customfield_` 형태로 넣는다.

이 기준으로 픽스처 E(워크플로 참조)는 검증기·후처리 함수·중첩 조건에서 확정 3건,
서드파티 숫자 arg에서 추정 1건이 나온다 — 의도한 그대로다.

## 5. [미사용] 라벨이 영원히 안 나오는 문제

Jira는 커스텀 필드를 만들면 자동으로 모든 필드 설정에 넣고 기본 컨텍스트를 준다.
아무 데도 안 쓴 필드도 참조 2건(필드 설정 1 + 컨텍스트 1)을 갖는다.
3장의 "[미사용] = 모든 참조 = 0"을 문자 그대로 구현하면 이 라벨이 절대 안 나온다.
실측: 픽스처 D(아무 곳에도 안 쓴 필드)가 [방치]로 찍혔다.

→ 참조 종류에 "사용 증거인가"(`ReferenceType.isEvidence()`)를 붙였다.
   필드 설정과 컨텍스트는 증거가 아니다(모든 필드가 자동으로 갖는다).
   다만 수집은 계속한다 — 필드 설정의 숨김/필수 표시는 삭제 판단에 실제로 필요하다
   (필수로 걸린 필드를 지우면 이슈 생성이 막힌다). 보여주고, 세지 않는다.

또 기획서 3장이 정의하지 않은 조합이 있다: 값 0 / 화면 0 인데 필터·가젯에서는 참조.
라벨을 새로 만들지 않고(3장: 임의로 늘리지 않는다) [방치]로 본다.

## 6. 라벨 타입 필드는 `customfieldvalue`에 값이 없다

라벨 타입 커스텀 필드에 값 3개를 넣었더니 `customfieldvalue`에는 0행,
`label` 테이블에 3행이 생겼다(`label.fieldid`가 커스텀 필드 ID).

기획서 5.1대로 `customfieldvalue`만 보면 값이 잔뜩 있는 라벨 필드가 "0건"으로 나온다.
이 도구에서 가장 나쁜 오류다 — 관리자가 데이터가 없다고 믿고 지우면 데이터가 사라진다.

→ `label` 테이블 집계를 쿼리 하나 더 추가해 합산한다.
   Rank처럼 앱 자체 AO 테이블에 저장하는 타입은 여전히 0이고, 그 한계는 UI 문구에 남긴다.

## 7. 권한 스킴 parameter 형식 (확인 5 후속)

REST로 `userCF` 항목을 만들고 DB에서 확인했다:

```
schemepermissions | perm_type=userCF | perm_parameter=customfield_10307
```

→ `customfield_<id>` 형태다. 알림 스킴도 같다(`notif_parameter=customfield_10307`).
   코드는 숫자 단독도 함께 받아들이도록 두었다(버전/타입에 따라 다를 수 있어서).

## 8. `/secure/admin/` 경로는 웹수도를 걸어주지 않는다

처음엔 "URL을 /secure/admin/ 아래 두면 Jira가 웹수도까지 걸어준다"고 적어놨었다.
실측해보니 틀렸다. 로그인만 한 세션(`/rest/auth/1/session`)으로:

| 화면 | 결과 |
|---|---|
| `/secure/admin/CustomFieldUsage.jspa` (애노테이션 없을 때) | **200, 표가 그대로 보였다** |
| `/secure/admin/ViewCustomFields.jspa` (Jira 기본) | "Administrator Access" 요구 |

즉 웹수도는 경로가 아니라 액션의 `@WebSudoRequired`가 결정한다.
이 도구는 필드 구성·값 분포·필터 내용을 전부 노출하므로 Jira 기본 관리 화면과 같은
수준을 지켜야 한다.

→ `sal-api`(Jira 8.13이 번들하는 4.2.0)를 provided로 넣고 액션에
  `@com.atlassian.sal.api.websudo.WebSudoRequired`를 붙였다. 붙인 뒤 같은 테스트:

| 화면 | 결과 |
|---|---|
| 로그인만 한 세션 | "Administrator Access" 요구 (기대) |
| 웹수도 통과 후 | 200, "Custom field usage" (기대) |
| REST (basic auth 관리자) | 200 — 주입 JS와 도구 스크립트가 계속 동작 |

웹수도는 권한 검사와 다른 층이다. `AdminGuard`의 `ADMINISTER` 검사는 그대로 둔다.

## 9. 스캔 스레드에는 i18n 컨텍스트가 없다

`FieldScreenSchemeItem.getIssueOperationName()`이 스캔 스레드에서 빈 값을 준다.
그래서 화면 체인에 `admin.issue.operations.create` 같은 원시 i18n 키가 노출됐다.
→ 로케일을 명시한 `I18nHelper.BeanFactory.getInstance(Locale.ENGLISH)`로 직접 번역한다.
   스캔 시점에 문자열로 굳는 값이라 뷰어 로케일을 따를 수 없어 영어로 고정했다.

## 10. `searchrequest.authorname`은 사용자 키다

실측: `JIRAUSER10000`. 그대로 화면에 내면 관리자가 누구인지 알 수 없다.
→ `UserManager.getUserByKey()`로 표시 이름으로 바꾼다(실패하면 키를 그대로 낸다).

# 추가 실측 (v1 배포 후, 사용자 지적으로 발견)

## 11. Jira 자신도 앱이 죽은 커스텀 필드를 목록에서 숨긴다

"Sprint / Epic Link는 기본 필드인데 왜 나오나"라는 지적에서 시작했다. 확인 결과
Sprint·Epic Link는 **기본 필드가 아니라 Jira Software가 만드는 커스텀 필드**다.
진짜 기본 필드(Summary, Assignee, Priority, Status, Labels 등)는 `customfield`
테이블에 없고 이 도구 목록에 나올 수 없다.

그런데 지적의 실제 근거는 맞았다 — 이 인스턴스의 Jira 관리 화면에는 정말 안 보인다.

| 출처 | 개수 |
|---|---|
| `SELECT COUNT(*) FROM customfield` | **24** |
| Jira의 `/rest/api/2/customFields` (= 관리 화면이 쓰는 것) | **18** |
| 차이 | Epic Link / Epic Name / Epic Status / Epic Color / Sprint / Rank |

Jira Agile이 비활성이라 Jira가 그 6개를 목록에서 숨긴다. 관리자 눈에는 없는 필드이고,
그래서 "기본 필드겠지"라고 오해하게 된다. 우리 도구가 6개를 더 보여주는 것은
[확인 3]의 DB 기준 목록 덕분이고, 의도된 차이다.

## 12. 앱이 잠근 필드가 초록 [미사용]로 찍히는 문제

Sprint / Rank는 값을 `AO_*` 테이블에 저장하고 화면 참조도 없어서 우리 집계로는
값 0 · 화면 0이 된다. 그 결과 **[미사용]("삭제 안전, 청소 1차 대상")** 라벨이 붙었다.
Sprint를 지우면 Jira Software 보드가 깨진다. 정리 도구가 낼 수 있는 최악의 신호다.

Jira는 이 필드들에 관리 화면에서 `LOCKED` 배지를 붙이고 **삭제 메뉴를 숨긴다.**
우리는 그 정보를 읽지 않고 있었고, 상세 화면에 삭제 링크까지 노출하고 있었다.

→ `ReferenceType.MANAGED`(앱 관리)를 추가했다. 라벨은 5개 그대로이고 `judge()`도
  손대지 않는다 — 이 참조가 위험으로 세지면서 자동으로 [위험]이 된다.
  잠긴 필드는 상세 화면에서 삭제 링크를 숨기고, 목록에 `locked` 배지를 붙인다.

### 왜 API가 아니라 테이블을 읽는가

`ManagedConfigurationItemService.getManagedCustomField()`는 `CustomField` 객체를
요구한다. 그런데 잠긴 필드 8개 중 6개가 정확히 "앱이 죽어서 객체가 없는" 상태다.
반면 `managedconfigurationitem` 테이블은 앱 상태와 무관하게 남아 있다:

```
item_id           | access_level | source
customfield_10000 | LOCKED | ...jira-development-integration-plugin:reserved-field-locked
customfield_10100 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10101 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10102 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10103 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10104 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10105 | LOCKED | com.pyxis.greenhopper.jira:reference-select-locked
customfield_10200 | LOCKED | com.atlassian.teams:field-locking-service
```

Story Points(10106)는 이 목록에 없다 → 잠기지 않은 평범한 숫자 필드이고,
Jira 관리 화면에도 `LOCKED` 배지가 없다. 실측 결과와 정확히 일치한다.
"앱이 만든 필드"와 "앱이 잠근 필드"는 다르고, 후자만 [위험]으로 올린다.

플러그인 표시 이름은 `PluginAccessor.getPlugin(key).getName()`으로 얻는다 —
앱이 비활성이어도 설치돼 있으면 객체를 주므로 "Jira Agile"이 그대로 나온다.

## 13. `managedconfigurationitem.managed`는 boolean이 아니다

`varchar(10)`에 문자열 `"true"`가 들어 있다(OfBiz indicator 타입).
`statement.setBoolean(1, true)`로 비교했더니 PostgreSQL이
`operator does not exist: character varying = boolean`으로 거부했다.

→ SQL에서 비교하지 않고 값을 그대로 받아 Java에서 판정한다.
  `"true"` / `"Y"` / `"t"` / `"1"`을 전부 받아들인다(DB·버전 방언 방어, 함정 10).

이 실패는 "확인 불가" 목록에 그대로 노출됐다. 함정 7의 설계가 의도대로 작동한 사례다 —
조용히 0건으로 넘어갔으면 잠긴 필드 8개가 계속 [미사용]으로 남았을 것이다.

## 14. 앱 jar 버전이 어긋나면 Jira Software가 아예 안 뜬다

테스트 환경에서 Jira Agile을 켜려다 실패해서 알게 된 것이다. `installed-plugins`의
앱 jar이 Jira 본체보다 높은 버전이면 OSGi 해석 단계에서 막힌다.

```
BundleException: Unable to resolve com.pyxis.greenhopper.jira:
  missing requirement osgi.wiring.package=com.atlassian.jira.i18n.terminology (version>=7.0.0)
```

`com.atlassian.jira.i18n.terminology` 는 Jira 8.13에 없는 패키지다(상위 버전에서
추가됨). `com.atlassian.jira.software-application` 도 이것에 딸려 함께 못 뜬다.

**이 상태가 오히려 11번·12번을 검증해 줬다.** Jira Software가 꺼져 있으면
Epic Link / Sprint / Rank 가 "타입 제공 앱이 죽은 필드"가 되는데, 우리는 존재 근거를
`customfield` 테이블에서 가져오므로 그대로 잡아낸다. Jira 자신의 관리 화면은
같은 필드를 숨긴다. 12번의 잠긴 필드 검출도 이 상태에서 나온 결과다.

애자일 **자체**의 동작(보드 설정 등)을 테스트해야 할 때만 버전을 맞춰야 한다.

# 코드 리뷰로 발견한 것 (v1.0.1)

외부 코드 리뷰(2026-09-09, v1.0.0 대상)가 지적한 것 중 실측으로 확인해 고친 것들이다.
전부 "정상 동작에서는 안 드러나고 실패 경로에서만 드러나는" 종류였다.

## 15. 재료 조회가 실패하면 라벨이 비지 않고 거꾸로 나온다

가장 심각한 발견이다. 값 집계가 실패했을 때 예전 코드는 필드마다 `valueCountUnavailable`
표시만 세우고 넘어갔다. 그런데 `issuesWithValue`는 0으로 남는다.

```
judge(0, screenRefs=0, risky=0, evidence=0) → UNUSED
```

즉 숫자 칸은 "확인 불가"인데 **라벨은 초록 [미사용]이고, 기본 정렬(cleanupOrder 0)이
그 필드를 목록 맨 위로 올린다.** 관리자가 가장 먼저 지울 후보로 본다. REST·CSV·주입
배지도 같은 라벨을 낸다.

재현(개발 인스턴스에서만):

```bash
docker exec <db-container> psql -U "$PGUSER" -d jira -c \
  "ALTER TABLE customfieldvalue RENAME TO customfieldvalue_x;"
curl -s -u "$JIRA_USER:$JIRA_PASS" -H 'X-Atlassian-Token: no-check' -X POST \
     "$JIRA_BASE/rest/janitor/1.0/scan"
```

**조치**: 재료를 두 등급으로 나눴다.

| 등급 | 대상 | 실패 시 |
|---|---|---|
| 필수 | `customfieldvalue`, `label`, `managedconfigurationitem` | `ScanFailedException` → 스캔 전체 실패 |
| 보조 | 나머지 수집기, 마지막 변경일 | "확인 불가" 목록 + 계속 |

판단 기준은 **"실패하면 라벨이 뒤집히나"**다. 뒤집히면 부분 결과를 내지 않는다.
`ReferenceCollector.isEssential()`이 그 표식이고, 잠긴 필드 수집기만 참이다.

측정 결과(고친 뒤): `state=FAILED`, `error=ScanFailedException: 값 집계 실패
(customfieldvalue)`, 이전 결과와 라벨은 그대로 유지, 화면에 빨간 실패 배너.

`valueCountUnavailable` 플래그는 이제 세워질 자리가 없어서 모델·REST·CSV·주입에서
제거했다. 항상 false인 필드를 남기면 "부분 확인이 가능하다"는 거짓 신호가 된다.

## 16. 잠긴 필드 조회 실패는 12번과 똑같은 구멍이었다

`managedconfigurationitem` 조회가 실패하면 MANAGED 참조가 0건이 되어 `isLocked()`가
거짓이 되고, Sprint / Epic Link / Rank 가 [미사용]으로 찍히면서 **상세 화면에
"Jira에서 삭제" 링크까지 열린다.** 12번에서 정상 경로는 고쳤지만 실패 경로가 남아
있었다. 이 조회를 필수 등급으로 올려 막았다.

측정: `state=FAILED`, `error=ScanFailedException: 필수 수집 단계 managed 실패`.

## 17. `Error`는 잡히지 않았다 — 8.17.1 배포에서 가장 현실적인 실패 모드

스캔 경로가 `catch (RuntimeException)`이었다. 그런데 이 플러그인은 8.13으로 컴파일해
8.17.1에서 돌리는 것이 전제이고, **그 전제가 깨질 때 나오는 예외는 전부 `Error`다** —
`NoSuchMethodError`, `NoClassDefFoundError`, `AbstractMethodError`.

놓치면 `finally`가 `running`만 내리고 진행률은 RUNNING에 박힌다. 화면의 `poll()`은
`state !== "RUNNING"`일 때만 멈추므로 **1.5초마다 영구 폴링**하고, 관리자는 이유를
볼 수 없다(로그에도 안 남았다 — `log.error`가 catch 블록에 있었다).

측정(임시로 `NoSuchMethodError`를 심어서): 고친 뒤 `state=FAILED`,
`error=NoSuchMethodError: test`, 로그에 스택 남음.

## 18. 실패가 화면 새로고침에 지워졌다

`poll()`이 RUNNING이 아니면 무조건 `window.location.reload()`를 했다. FAILED도
RUNNING이 아니므로, 실패 메시지를 넣은 직후 페이지를 새로 그려 지웠다. 서버 쪽에도
실패 정보가 없어서 **두 번째 이후의 스캔이 실패하면 이전 스캔 결과가 최신인 것처럼
그대로 남았다.**

조치: `ScanService.getLastFailure()`로 실패를 따로 보관하고, 목록 화면이 서버측에서
빨간 배너로 그린다. 새로고침해도 남는다. `isResultStale()`(실패 시각 > 결과 완료
시각)이면 "아래 표는 이전 스캔의 결과다"를 함께 낸다. FAILED에서는 재로드하지 않는다.

## 19. 반사형 XSS — 언어 토글이 `fieldId`를 그대로 붙였다

```java
return "CustomFieldUsage.jspa?lang=ko" + (fieldId == null ? "" : "&fieldId=" + fieldId);
```

`fieldId`는 요청 파라미터 원본이고 템플릿은 `<a href="$action.koUrl">`로 심는다.
숫자로 파싱되지 않으면 `doExecute`가 목록 템플릿으로 떨어지므로
`?fieldId="><img src=x onerror=...>` 가 href를 탈출한다.

조치: 파싱에 성공하고 실제로 존재하는 필드일 때만 숫자를 보관해(`selectedFieldId`)
그것만 `customfield_<id>` 형태로 다시 내보낸다. 유효하지 않은 값을 URL에 되돌려 줄
이유가 없다.

측정: 페이로드를 주면 토글 링크에 `fieldId`가 아예 없고 `<img onerror>`도 없다.
유효한 ID(`10305` / `customfield_10305`)는 둘 다 `&fieldId=customfield_10305`로 정규화된다.

## 20. 같은 참조가 두 번 세졌다

`Reference`에 `equals`/`hashCode`가 없었다. 2차원 통계 가젯의 `xstattype`/`ystattype`
처럼 한 대상이 같은 필드를 두 자리에서 가리키면 참조가 2건이 되고, GADGET은 사용
증거로 세므로 **[미사용]이 [방치]로 뒤집힌다.** 상세 화면에도 같은 행이 두 줄 나온다.

조치: `(종류, targetId, targetName, detail, detailI18nKey, risky)`로 동일성을 정의하고
`FieldUsage.addReference()` 입구에서 중복을 막는다. `projects`·`adminUrl`은 비교에서
뺐다 — 같은 대상에서 파생된 값이라 판단에 새 정보를 주지 않고, 넣으면 순서 차이만으로
중복이 살아남는다.

## 21. 그 밖에

- **CSV 인젝션**: `= + - @` 외에 **탭(0x09)·CR(0x0D)**로 시작하는 값도 Excel이 수식으로
  해석한다. 필드 이름은 관리자만 만들지만 필터 이름은 아무 사용자나 만든다.
- **`LIKE`의 `_`는 와일드카드**다. `'customfield_%'`에 `ESCAPE`를 줬다. 현재 데이터로는
  결과가 같지만 의도한 쿼리가 아니고 다른 DB에서 오탐이 된다.
- **Velocity는 없는 오버로드를 조용히 문자열로 출력한다.** 상세 화면 `<title>`이
  `text(key, arg)` 2-arg로 부르는데 오버로드가 없어서 표현식이 그대로 렌더됐다.
  `text(String, Object)`를 추가했다.
- **권한 문서가 코드와 달랐다.** 코드는 `ADMINISTER`(Jira 관리자), 문서는 "시스템
  관리자"였다. 코드가 맞다 — Jira 기본 `ViewCustomFields.jspa`와 같은 기준이어야
  한다. README를 고쳤다.

## 22. 단위 테스트를 넣었다 (19개)

리뷰의 구조적 지적이 맞았다. `judge()`는 Jira 없이 테스트할 수 있는 순수 함수인데
테스트가 0개였고, **15번 버그는 그 진리표의 첫 줄이 그대로 드러내는 사실이었다.**

- `UsageStatusTest` — `judge()` 진리표, 정리 순서, 라벨 5개 고정
- `FieldsResourceTest` — `parseFieldId` 경계값(XSS 페이로드·SQL·Long 범위 초과 포함),
  `quote()` CSV 인젝션

`atlas-mvn -o test`로 돈다. 실제로 한 건 잡았다 — 정렬 순서를 활성 → 고아 데이터로
잘못 가정했는데, 코드가 맞고(고아 데이터가 먼저) 내 가정이 틀렸다. 정렬은 "지워도
되는 순"이 아니라 "손봐야 하는 순"이다.

# 재리뷰로 발견한 것 (v1.0.2)

v1.0.1 을 대상으로 한 재리뷰(2026-09-09)와, 그 검증 중 내가 발견한 것이다.

## 23. 목록 화면의 에러 안내가 한 번도 표시되지 않았다

두 리뷰가 모두 놓쳤고 재리뷰의 N1 을 실측하다 발견했다. `list.vm` 이

```velocity
#if ($action.hasErrorMessages())
```

로 쓰고 있었는데 **webwork1 에는 `hasErrorMessages()` 라는 메서드가 없다.**
실제 이름은 `getHasErrorMessages()` 이고, Velocity 는 메서드 호출 문법에서 그것을
찾지 못해 조용히 false 로 평가한다. 에러도 로그도 남지 않는다.

결과: 없는 필드 ID나 스캔 전 상태로 들어온 관리자가 **아무 설명 없이 목록만 봤다.**
v1.0.0 부터 그랬다.

`hasAnyErrors()` 로 고쳤다 — `JiraActionSupport` 의 public 메서드이고 Jira 관용
표현이다. `getHasErrorMessages` 프로퍼티 접근보다 의도가 분명하다.

**교훈**: Velocity 는 없는 메서드를 에러로 만들지 않는다. 조건식에서 그러면
분기 전체가 조용히 죽는다. 24번(N1)과 같은 성질이고, 화면 문구를 넣을 때
"렌더된 HTML 에 실제로 나오는지"를 봐야 한다.

## 24. `{0}` 이 있는 문구를 1-arg 로 불렀다 (재리뷰 N1)

`janitor.fields.detail.notFound` 는 `{0}` 을 갖는데 호출이 1-arg 였다. 치환이
일어나지 않아 화면에 `{0} 의 상세를 볼 수 없습니다` 가 나올 상황이었다 — 다만
23번 때문에 애초에 표시되지 않아 아무도 못 봤다. 둘을 함께 고쳤다.

측정: `?fieldId=customfield_99999` → `customfield_99999 의 상세를 볼 수 없습니다`.
XSS 페이로드를 넣어도 안전하다(webwork 와 `$action.escape` 로 이중 이스케이프 —
표시가 지저분하지만 안전한 쪽 실패라 그대로 두고, 길이만 40자로 자른다).

## 25. 중복 제거가 스킴 참조를 뭉갰다 — v1.0.1 에서 내가 만든 회귀 (재리뷰 N8)

v1.0.1 에서 `Reference.equals` 를 넣어 중복을 막았는데, 스킴 참조의 동일성 키가
`(종류, 스킴이름, 스킴ID, "userCF", risky)` 라서 **한 스킴이 같은 필드로
Browse / Edit / Assign 세 권한을 주면 세 참조가 완전히 같은 키였다.** 3건이 1건으로
합쳐졌다.

라벨은 그대로 [위험]이지만 상세 화면에서 "세 군데가 걸려 있다"는 사실이 사라진다.
[위험] 필드의 상세는 관리자가 **무엇을 손봐야 하는지 읽는 유일한 곳**이라, 거기서
정보가 줄면 라벨만 남고 조치가 불가능해진다.

조치: `SchemeEntity.getEntityTypeId()` 를 `targetId` 에 함께 넣는다
(`"0/BROWSE_PROJECTS"` 형태 — 8.13 에서 권한 키 이름을 준다).

**픽스처가 이걸 못 잡은 이유**가 중요하다. 픽스처 F 는 권한 항목이 하나여서
합칠 것이 없었다. 항목이 하나면 중복 제거 버그가 절대 드러나지 않는다.
픽스처 F 를 세 권한으로 늘렸고, 그 결과 위험 참조가 2건 → 4건(권한 3 + 알림 1)이
됐다. 회귀 고정은 `ReferenceTest.스킴의_권한이_다르면_다른_참조다` 가 담당한다.

## 26. `isEssential` 의 반경이 필요보다 넓었다 (재리뷰 N2)

`isEssential` 은 `collect()` 메서드 전체에 걸리는데, 정작 필수인 것은 DAO 조회
한 줄이다. 표시용 이름을 얻는 `pluginName()` 이 `PluginAccessor` 에서 `Error` 를
내면 — 앱 업그레이드·재설치 중 현실적으로 일어난다 — 정작 필요한 정보는 이미 손에
들고 있는데 스캔이 죽는다.

`pluginName()` 의 catch 를 `Throwable` 로 넓혀 실질 반경을 DAO 조회로 좁혔다.
필수 등급은 "실패하면 라벨이 뒤집히는 조회"에만 걸려야 한다.

## 27. 필드 목록이 반쪽인 것을 "확인 불가" 한 줄로 두었다 (재리뷰 N3)

`customfield` 테이블을 못 읽으면 `CustomFieldManager` 목록만으로 진행하는데,
그 API 는 **타입 제공 앱이 비활성인 필드를 빼고 준다**(3번·11번) — 정리 1순위
후보가 바로 그 필드들이다. 라벨이 뒤집히지는 않으니 스캔을 실패시키지는 않지만,
실패의 성격이 "일부 항목을 못 읽었다"가 아니라 **"목록이 반쪽이다"** 라서 화면 맨
아래 목록에 두면 표가 완전하다고 읽힌다.

`ScanResult.isFieldListDegraded()` 를 두고 화면 맨 위 경고 배너로 올렸다.
등급 기준을 한 칸 넓힌 셈이다 — "라벨이 뒤집히나?" 에 "판정 대상이 사라지나?" 를
더했지만, 후자는 스캔 실패가 아니라 배너로 대응한다.

## 28. 클라이언트도 조용히 실패했다 (재리뷰 N6·N7, #6 뒤쪽의 대안)

불변 7("실패를 조용히 누락시키지 않는다")이 서버측에만 적용돼 있었다.

- `POST /scan` 이 403 이면 `showProgress(null)` 이 즉시 반환하고, **버튼은
  disabled 로 남고 폴링이 시작된다.** 관리자에게는 "눌렀는데 아무 일도 없고 버튼이
  죽었다"로 보인다.
- `poll()` 은 `code !== 200` 이면 아무것도 하지 않는다. 웹수도 세션이 만료되면
  조용히 멈춘다.
- 실패 메시지가 파란 정보 박스(`aui-message-info`)에 담겼다. 가장 중요한 순간에
  색이 반대다.

조치: 401/403 은 폴링을 멈추고 버튼을 되살리고 "세션이 만료되었습니다" 를 낸다.
그 밖의 4xx/5xx 는 일반 실패 문구. 409(이미 실행 중)는 실패가 아니다.
진행률 박스 클래스를 상태에 따라 바꾼다(RUNNING=info, FAILED=error).

Nashorn 으로 다섯 경로를 검증했다: 202 정상(파란 박스·폴링 시작),
409 중복(실패 아님), FAILED(빨간 박스·재로드 안 함), DONE(재로드), 401(멈춤·안내).

## 29. REST 에 `@WebSudoRequired` 를 붙이지 않기로 결정했다 (#6 뒤쪽)

재리뷰가 결정적인 근거를 줬다. **웹수도 승격은 시간 제한이 있고(기본 10분 수준),
대규모 인스턴스의 스캔은 그보다 오래 걸릴 수 있다.** REST 에 웹수도를 걸면 스캔
도중 승격이 만료되어 폴링 XHR 이 401 로 떨어진다. 스캔은 서버에서 계속 도는데
화면은 진행률을 잃는다.

지금 구조 — 화면 진입에는 웹수도(`@WebSudoRequired` on action), REST 에는 관리자
권한 재검사(`AdminGuard`) — 가 그 상황에서 살아남는다. 얻는 것(이미 관리자 권한
검사를 통과한 호출에 한 겹 더)보다 잃는 것이 크다.

대신 28번의 클라이언트측 401/403 처리를 넣었다. 웹수도를 안 걸어도 세션 만료·권한
상실 시 화면이 조용히 죽지 않게 하는 것이 실질적인 보강이다.

## 30. 한국어 문구 3개가 반말이었다 (재리뷰 N4)

`scanFailed.*` 세 줄만 평서체였고 나머지 UI 문구는 전부 존댓말이었다. 하필 빨간
배너라 눈에 제일 잘 띈다. 리뷰 문서를 평서체로 쓰라는 요청이 제품 문구까지 옮겨간
것이다 — 제품 문구는 기존 등록을 따른다.

## 31. 그 밖에

- **중복 검사가 O(n²)였다**(재리뷰 N5). `List.contains` 를 썼는데, 전이 화면 참조는
  (워크플로, 전이)마다 1건씩 생기므로 공용 전이 화면을 쓰는 워크플로 100개 ×
  전이 20개면 한 필드에 2,000건이고 비교가 200만 회다. `hashCode` 가 이미 있으니
  `HashSet` 하나로 O(1)이 됐다.
- **테스트 43개**로 늘렸다. 재리뷰가 우선순위 1로 꼽은 `ReferenceTest` 는 25번 회귀를
  고정한다 — `equals` 가 관대해지면 참조가 조용히 사라지고 로그도 problem 도 안
  남는다. `ScanContextTest` 는 오탐 방지 로직(4번)을, `JanitorDaoTest` 는
  `isTrue`(13번)를 고정한다.
- JUnit 4.10 에는 `assertNotEquals` 가 없다(4.11부터). 오프라인 빌드를 유지하려고
  버전을 올리지 않고 `assertFalse(a.equals(b))` 로 썼다.

## 32. 이슈 네비게이터 컬럼 수집기 (v1.1.0)

기획서 5.3(9)의 마지막 남은 수집기다. DAO 쿼리는 v1.0.0 부터 있었고 수집기만 없었다.
집계(`getColumnLayoutCounts()`)를 행 조회(`getColumnLayoutRows()`)로 바꿔 대체했다 —
"3곳"은 관리자가 할 수 있는 일을 알려주지 않는다. 어디인지가 갈려야 조치가 정해진다.

**컬럼 설정은 셋이다.** `columnlayout` 의 두 컬럼으로 구분한다(실측):

| username | searchrequest | 뜻 |
|---|---|---|
| NULL | NULL | 시스템 기본 컬럼 |
| NULL | 필터 ID | 그 필터의 컬럼 |
| 사용자 키 | NULL | 그 사용자의 개인 컬럼 |

- **`columnlayout.username` 은 이름이 아니라 사용자 키다** — 실측값 `JIRAUSER10000`.
  `searchrequest.authorname`(함정 목록에 이미 있음)과 같은 함정이라 같은 방식으로
  `UserManager.getUserByKey()` 로 푼다. 조회 실패는 표시 문제일 뿐이라 키를 그대로 낸다.
- **시스템 기본 컬럼에는 관리 화면 링크를 붙이지 않는다.** 8.13 에서 후보를 전부
  쳐봤는데 `ViewIssueColumns!default.jspa` · `ViewIssueColumns.jspa` ·
  `ViewDefaultColumnLayout.jspa` 가 모두 404였다. `actions.xml` 에 column 관련 액션이
  없고 번들 플러그인(jira-issue-nav-plugin 10.0.6)의 디스크립터에도 관리 액션이 없다.
  없는 링크를 붙이면 관리자가 그 화면을 찾는 데 시간을 쓴다.
- **개인 설정은 필드마다 한 건으로 합친다.** 사용자 수만큼 참조를 만들면 인기 있는
  필드 하나에 수백 행이 생겨 상세 화면이 못 쓰게 되고, 관리자가 할 수 있는 일도 없다
  (남의 개인 설정은 관리 화면에서 못 고친다). 대신 부가 정보에 `2 · Janitor Tester, bskim`
  처럼 사람 수를 앞에 두고 이름 일부를 남긴다(5명까지, 나머지는 `+N`).
- **사용 증거로 세고 위험으로는 세지 않는다.** 누군가 목록에 띄우려고 직접 골라 넣은
  것이라 증거이고, 지워도 컬럼 하나가 빠질 뿐 동작은 안 깨진다.
  Jira 가 기본 컬럼에 미리 넣어두는 커스텀 필드는 **Development 하나뿐**이고(실측)
  그 필드는 앱이 잠근 필드라 이미 [위험]이다 — 필드 설정·컨텍스트 같은
  "모든 필드가 자동으로 갖는" 함정(5번)에 해당하지 않는다.

**대상 이름이 데이터에 없는 첫 참조다.** 시스템 기본과 개인 설정은 이름이 없다.
스캔 스레드에는 보는 사람의 로케일이 없으므로(10번) 이름을 그때 만들 수 없다.
그래서 `targetName` 을 비우고 종류를 `detailI18nKey` 로 넘긴 뒤, **`detail.vm` 이
`targetName` 이 없으면 그 키를 대상 자리에 그린다.** 빈 칸으로 두면 수집 실패로 읽힌다.

**"새 참조 종류 추가 절차"가 5단계가 아니었다.** 실제로는 CSV 헤더와
`FieldSummaryDto` 도 종류를 이름으로 하나씩 열거한다. 설명서(`help.vm`)와 상세 화면은
열거형을 순회하므로 자동이지만, 그 둘은 손으로 고쳐야 한다. CLAUDE.md 의 절차를 고쳤다.

**픽스처 J**: 필터 컬럼 2개 + 개인 컬럼 2명. 둘씩 만드는 이유는 픽스처 F 와 같다 —
대상이 하나뿐이면 중복 제거가 참조를 뭉개도 픽스처가 통과한다. 개인 컬럼 REST는
**본인 계정으로 불러야 한다**: `PUT /rest/api/2/user/columns?username=<남>` 은 200을
주지만 실제로는 **부르는 사람의 설정**이 바뀐다(실측: DB에 그 사람 행이 안 생겼다).
`JIRA_SECOND_PASS` 가 없으면 개인 컬럼은 한 명으로 진행한다.

**목록 화면에는 컬럼을 추가하지 않았다.** 목록의 숫자 컬럼은 v1.0 부터
화면·워크플로·필터·가젯 네 종류만 보인다(스킴·필드설정·컨텍스트·앱관리도 안 보인다).
컬럼 참조는 참조 합계와 상세 화면, CSV(`columnLayouts` 열), REST 에 들어간다 —
목록에서 안 보인다고 안 세는 것이 아니다.

실측 결과(8.13): 필드 A(`customfield_10302`) 컬럼 참조 3건(필터 2 + 개인 1건·2명),
Development(`customfield_10000`) 1건(시스템 기본). 한국어·영어 화면 양쪽에서
대상·위치 칸이 의도대로 그려지는 것을 렌더된 HTML 에서 확인했다.

## 33. 스캔 결과를 재기동 후에도 남긴다 (v1.2.0)

v1.5 계획의 "AO 스냅샷" 항목이다. **결과는 AO 가 아니라 SAL `PluginSettings` 에 둔다.**

**AO 를 안 쓴 이유.** AO 의 `ActiveObjects` 서비스는 플러그인마다 다른 인스턴스를 주는
OSGi `ServiceFactory` 다. `ComponentAccessor.getOSGiComponentInstanceOfType` 으로 꺼내면
우리 것이 아니고(또는 null), 제대로 주입받으려면 spring-scanner 를 들여야 한다.
그러면 지금 `AdminOnlyCondition` 이 기대고 있는 Spring 부트스트랩(빈 없는
`plugin-context.xml` + `Spring-Context *`, 9번)을 다시 배선해야 한다. 그 자리는 이미 한 번
조용히 깨졌던 곳이다. "문서 하나를 기억한다"는 요구에 그 위험을 살 이유가 없다.
`sal-api` 는 이미 provided 로 쓰고 있어 새로 들이는 것도 없다.

**실측한 것.**

- `ComponentAccessor.getOSGiComponentInstanceOfType(PluginSettingsFactory.class)` 로
  얻어진다. 값은 `propertyentry.propertytype = 6` + `propertytext.propertyvalue`(TEXT)로
  들어간다 — 1,000자 문자열이 그대로 왕복했다. PostgreSQL TEXT 는 길이 제한이 없으므로
  **압축도 분할도 하지 않는다.** 필드 24개 스냅샷이 31KB였다(≈1.3KB/필드).
  필드 300개면 400KB 수준이다.
- JSON 은 `com.atlassian.jira.util.json.JSONObject`(jira-api)로 만든다. Jackson 을 직접
  import 하면 8.13 에서 되고 8.17.1 에서 깨지는 종류의 의존이 하나 는다.

**`INFO` 로그는 이 인스턴스에서 버려진다.** 우리 패키지에서 로그에 실제로 남은 것은
`WARN`/`ERROR` 뿐이었다(실측: 로그 전체에서 `c.b.j.j.` 는 WARN 2건·ERROR 4건).
그래서 "스냅샷을 복원했다" / "판이 달라 버렸다" / "PluginSettingsFactory 를 폴백 경로로
얻었다" 세 줄을 **WARN 으로** 남긴다. 표에 찍힌 시각이 이번 기동에서 스캔한 것인지
복원된 것인지는 문제를 쫓을 때 첫 번째로 알아야 하는 사실이라 사라지면 안 된다.
(처음에 INFO 로 뒀다가, 로그에 아무것도 안 남아 "OSGi 경로가 통했다"고 잘못 읽을 뻔했다.)

**스키마·플러그인 버전이 다르면 버린다.** 관대하게 읽으면 안 된다 — v1.0.2 가 저장한
스냅샷에는 컬럼 참조(32번)가 없어서, 컬럼으로만 쓰이던 필드가 [미사용]으로 나온다.
정보가 없는 것이 삭제 신호로 바뀌는 것이 이 도구 최악의 실패다(15번).
버리면 "아직 스캔한 적 없음"이 되고 관리자는 스캔을 다시 누른다 — 잃는 것은 시간뿐이다.

**실패도 함께 저장한다.** 결과만 남기면 재기동 뒤 실패한 스캔의 배너가 사라지고 옛 표만
남는다 — 18번이 재기동이라는 새 옷을 입고 그대로 재현된다. 스캔이 끝날 때마다
결과와 실패를 <b>한 봉투에</b> 넣는다(성공: 결과+null / 실패: 이전 결과+실패).

**읽기는 처음 물어볼 때 한 번.** 플러그인 활성화 시점에는 SAL 서비스가 아직 안 떠 있을
수 있다. 메모리는 DB 행의 캐시다 — 없으면 읽어 오고(read-through), 스캔이 끝나면
쓴다(write-through). **Data Center 에서 스캔하지 않은 노드는 자기가 마지막으로 읽은
스냅샷을 계속 보여준다.** v1.2.0 은 노드 간 무효화를 하지 않는다. 그래도 v1.1.0 보다는
낫다 — 전에는 노드마다 "결과 없음"에서 시작했다.

**실측 확인(8.13)**: 스캔 → 재배포(싱글턴이 사라진다) → 목록 화면에 표 24행과
"마지막 스캔 02:07"이 그대로 나온다(로그에 "스냅샷을 복원했다"). 저장된 JSON 의
`pluginVersion` 을 `1.0.2` 로 바꾸고 재배포하면 결과가 0건이 되고 "판이 달라 버렸다"가
남는다. `failure` 를 주입하고 재배포하면 빨간 배너와 "아래 표는 이전 스캔의 결과입니다"가
다시 나온다.
