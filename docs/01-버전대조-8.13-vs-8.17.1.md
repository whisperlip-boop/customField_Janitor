# 8.13.0 ↔ 8.17.1 대조 결과

목적: 이 플러그인은 **8.13.0으로 컴파일해 8.17.1 운영 서버에 올린다**.
그 가정이 성립하는지를 가정이 아니라 실측으로 확인한다.

측정일: 2026-09-09 (v1.0.0) / **2026-09-10 (v1.2.1 재대조 — 아래 2차 항)**

## 환경

두 환경을 함께 쓴다. 어느 하나가 다른 하나를 대체하지 않는다.

| | docker 8.13.0 | atlas-run 8.17.1 |
|---|---|---|
| 기동 | 상시 (직접 띄운 docker) | `sleep infinity \| atlas-run -Pjira817` (`localhost:2990/jira`) |
| 계정 | `JIRA_USER` / `JIRA_PASS` 환경변수 | admin / admin (AMPS 기본값) |
| DB | PostgreSQL 11 (운영과 같은 계열) | **H2** |
| 라이선스 | 직접 준비 | AMPS timebomb (자동, 수 시간) |
| Jira Software | 앱 버전 불일치로 비활성 | `<applications>`로 설치, 활성 |
| 웹수도 | 켜짐 | **AMPS가 인스턴스 전체에서 끔** |
| 덮는 축 | PostgreSQL 방언, 앱이 죽은 필드 | 상위 버전 API·section 키, SQL 이식성, Software 필드 |

**컴파일은 두 프로필 모두 `jira-api:8.13.0`으로 고정된다**(`dependency:list`로 확인).
`jira817` 프로필은 실행 버전만 올린다. 그래서 이 대조가 "낮은 쪽으로 컴파일한 jar이
높은 쪽에서 도는가"를 실제로 검증한다.

워크플로 4건이 양쪽에서 같다는 게 특히 중요하다. 이 플러그인에서 가장 깊은

8.13 쪽의 필드 24개 / 8.17.1 쪽 22개, 필터·가젯 수 차이는 **픽스처 이력 차이**다
(8.13에는 초기 스크립트 시행착오로 동명 필드가 더 많고, 깨진 JQL 필터와 SQL로 넣은
가젯 행이 8.13에만 있다). 버전 차이가 아니다.

## 조치한 것

**행 구조 차이(5b)가 실제 회귀였다.** 8.17.1의 커스텀 필드 표는 일괄 작업
체크박스 칸이 이름 칸 앞에 온다(`showBulkCheckbox`). `inject.js`가 "첫 `<td>`"를
이름 칸으로 가정하고 있어서 배지가 체크박스 칸에 들어갔을 것이다.

→ 이름 칸을 세 단계로 찾도록 고쳤다: `td.customfield-name-cell` → 이름 요소(`strong`)의
  부모 td → 첫 td. 어느 버전에서 무엇이 바뀌어도 이름 요소만 찾으면 맞는 칸에 붙는다.
  8.13/8.17.1 두 행 구조를 Nashorn에 넣어 네 경우 모두 검증했다.

**중복 배지도 제거했다.** 8.17.1은 잠긴 필드에 자체 `LOCKED` 로젠지를 이미 붙인다.
Jira 것이 있으면 우리 `locked` 배지를 생략한다.

## 8.17.1에서 새로 발견한 것 — 기획서 [확인 1]의 전제가 흔들린다

8.17.1의 커스텀 필드 관리 화면 소스(`viewCustomfields.soy`)에 이런 것이 있다:

```
{if $showUsageData}
    <th class="customfield-updates sortable">  {getText('admin.issuefields.last.value.update')}
    <th class="customfield-values sortable">   {getText('admin.issuefields.issues.with.value')}
```

그리고 사이드바에 **"Custom fields optimizer"**(`/secure/admin/CustomfieldsAnalyzer.jspa`)와
**"System fields"** 항목이 새로 있다. 행 템플릿에는 일괄 삭제 체크박스와 `isTrusted`
플래그도 생겼다.

즉 **"값이 있는 이슈 수"와 "마지막 값 변경일"을 Jira 8.17.1이 자체 제공할 수 있다.**
기획서 [확인 1]은 "어떤 버전에서도 제공되지 않는다. 이게 핵심 가치다"라고 적었는데,
8.17.1에서는 코드가 존재한다. 8.13의 `customfield` 테이블에 있던 정체불명의
`issueswithvalue` / `lastvalueupdate` 컬럼도 이 기능의 것이다.

단, **기본값은 꺼져 있다**:

```js
showUsageData: FeatureManager.isFeatureEnabled('jira.customfields.cleanup.identification')
```

이 인스턴스의 활성 다크피처 목록에 그 키가 없고, REST 응답에도 `issuesWithValue` 필드가
없으며 `isTrusted: false`다. 관련 속성 키(`com.atlassian.jira.issue.fields.usage.init.required`,
`...usage.calc.date`)로 보아 켜려면 통계 초기화 배치가 필요하다.
(다크피처를 켜보려 했으나 관리 액션이 403으로 거부해 실제 화면은 확인하지 못했다.)

### 그래서 이 도구의 가치는 어디에 남는가

Jira 8.17.1이 다크피처를 켰을 때 주는 것 = 축 A(값 있는 이슈 수, 마지막 변경일) + 일괄 삭제.

이 도구만 주는 것 = **축 B/C 전부**:

- 워크플로 참조 (전이 이름 + 조건/검증기/후처리 함수 위치까지)
- 필터 참조 (JQL, 이름 참조와 `cf[ID]` 참조 양쪽)
- 권한 / 알림 / 이슈 보안 스킴 참조
- 대시보드 가젯 참조
- 필드 설정의 표시/숨김/**필수**
- 화면 → 화면 스킴 → ITSS → **프로젝트** 체인
- 세 축을 합친 상태 라벨과 판단 요약
- "확인 불가" 목록
- 앱이 죽어 Jira 목록에서 사라진 필드 (8.13에서 24 vs 18)
- 이름 중복 경고, 이슈 수 / 값 행 수 구분, CSV 내보내기

축 A는 8.17.1에서 중복될 수 있다. 축 B/C는 어느 버전도 제공하지 않는다.
운영에 올린 뒤 다크피처를 켤 계획이라면, 축 A는 Jira 것을 쓰고 우리 목록에서는
보조 지표로 내려도 된다 — 다만 라벨 판정에는 계속 필요하다.

## 결론

**8.13.0으로 컴파일한 jar이 8.17.1에서 그대로 동작한다.** 모듈 5개 전부 활성화되고,
section 키·행 후크·타입 문자열·직접 SQL·상태 판정이 모두 일치했다. deprecation 경고도
없다. 다만 **관리 화면 표의 열 구조는 바뀌었고**, 그건 코드를 고쳐서 두 버전 모두를
지원하게 했다.

재현:
```bash
sleep infinity | atlas-run -Pjira817
JIRA_BASE=http://localhost:2990/jira JIRA_USER=admin JIRA_PASS=admin python3 tools/make-testdata.py
JIRA_BASE=http://localhost:2990/jira JIRA_USER=admin JIRA_PASS=admin ./tools/make-workflow-fixture.sh
./tools/probe-jira.sh http://localhost:2990/jira admin admin
./tools/probe-jira.sh "$JIRA_BASE" "$JIRA_USER" "$JIRA_PASS"    # 8.13 기준값
```


## 2차 대조 — v1.2.1 (2026-09-10)

1차 대조는 v1.0.0 시점이었다. 그 뒤 v1.0.1 ~ v1.2.1 은 docker 8.13 에서만 돌렸고,
특히 `catch(Throwable)`(docs/00 17번)은 **8.17.1 배포에서만 나오는 실패 모드를 위한
수정인데 그 환경에서 한 번도 실행되지 않았다.** 그 공백을 메운 기록이다.

방법: `sleep infinity | atlas-run -Pjira817` 로 8.17.1 을 띄우고, docker 인스턴스와
같은 픽스처(`make-testdata.py` + `make-workflow-fixture.sh`)를 REST 로 그대로 올린 뒤
UPM 으로 `janitor-1.2.1.jar` 을 설치했다.
